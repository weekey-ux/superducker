## 修复：builder.bat 编译失败（9 个错误）

IDE 的 read_lints 未报错但 `dotnet build` 报 9 错，说明**必须以实际编译为准**。根因与修复：

1. **CS0122 ×2** — `MainViewModel.BuiltInDark()/BuiltInLight()` 声明为 `private static`，但 `MainWindow.xaml.cs` 跨类调用 → 改为 `public static`。
2. **CS0103 ×2** — `MainViewModel.cs` 用了 `JsonSerializer` 与 LINQ 的 `Where/Select/First`，但缺 `using System.Text.Json;` 和 `using System.Linq;` → 补齐。
3. **CS0246 / CS0104 / CS0176 ×3（同一根因）** — `ThemeEditorDialog.xaml.cs` 顶部写了 `using System.Windows.Forms;` 导致：`Button` 在 WPF/WinForms 间二义、`HorizontalAlignment` 解析到 WinForms 枚举、且 WinForms using 遮蔽后 `Rectangle` 找不到。
   → **正解：不要为了一个 ColorDialog 而 using 整个 WinForms 命名空间**。改为移除该 using，补 `using System.Windows.Shapes;`（Rectangle），ColorDialog 用完全限定名 `System.Windows.Forms.ColorDialog`，`HorizontalAlignment` 显式写 `System.Windows.HorizontalAlignment.Right`，并给按钮补 `DockPanel.SetDock(btn, Dock.Right)` 使其在 DockPanel 内真正右对齐。
4. **CS0029 ×2** — `SettingsDialog` 是 `UserControl` 而非 `Window`，`new ThemeEditorDialog{ Owner = this }` 类型不符 → 改为 `Owner = Window.GetWindow(this)`。

验证：`dotnet build SuperDucker.App -c Release` → 0 警告 0 错误。用户拒绝运行完整 builder.bat，故仅验证 App 项目。

### 经验教训
- **WPF 项目中引用 WinForms 类型一律用完全限定名**，避免 using 级命名冲突（Button/Label/HorizontalAlignment/MessageBox 等大量同名类型）。
- `SettingsDialog` 是 UserControl，弹窗设 Owner 必须走 `Window.GetWindow(this)`。
- PowerShell 下执行命令：`cd A && B` 不可用，要用 `cd A; B`；构建输出被吞时重定向到文件再读。

## 修复：自定义主题下拉框样式不跟随主题

`CmbThemePreset` 只设了 `Background/Foreground/BorderBrush`，但这几个属性在 WPF ComboBox 默认模板里只影响可编辑文本区与外框；**下拉弹出的 Popup 项、下拉箭头、Item 容器**仍走系统默认模板（白底黑字 + 系统箭头），所以即使主题切换下拉列表内文字也始终是黑的。

**正解**：不要试图靠属性改默认模板，必须显式应用 `DarkComboBoxStyle` + `DarkComboBoxItemStyle`（ShopPanel 的分类 ComboBox 就是这么做的）。这俩样式内部用 DynamicResource 引用 `BgCardHoverBrush / TextPrimaryBrush / BgDarkBrush / TextSecondaryBrush`，主题切换时会自动跟随。

### 经验
- WPF 控件换肤不要用 Background/Foreground 属性打补丁，要换 Style/ControlTemplate；属性只覆盖默认模板里的部分槽位。
- 项目内已有的换肤 ComboBox 样式叫 `DarkComboBoxStyle` / `DarkComboBoxItemStyle`（在 `App.xaml` 291/382 行），新加 ComboBox 应当沿用而不是自创。

## 修复：ComboBox 闭合态显示对象类型而非 Name

`CmbThemePreset` 绑 `ItemsSource=ThemePresets`（自定义对象集合）+ `DisplayMemberPath="Name"`。下拉项正常显示 "Dark"/"Light"，**但闭合态显示框**显示的是 `"SuperDucker.App"` 之类。

**根因**：WPF ComboBox 的 `DisplayMemberPath` 仅生成 `ItemTemplate`（用于下拉项），**不会**自动生成 `SelectionBoxItemTemplate`。闭合态的 ContentPresenter（App.xaml `DarkComboBoxStyle` 第 338 行）绑定的是 `SelectionBoxItemTemplate`，缺省为 null → 走默认 ContentPresenter → 用对象 `ToString()` → 退化为类型全名（"SuperDucker.App" 是 namespace 部分，截断显示）。

**走过的弯路**：先尝试在 XAML 里显式写 `<ComboBox.SelectionBoxItemTemplate>`，编译报 `error MC3065: "SelectionBoxItemTemplate"属性是只读的，且无法从标记设置`。该属性是**只读依赖属性**，只能由 WPF 内部推导，不能手写。

**正解**：去掉 `DisplayMemberPath`，改为显式设置 `ItemTemplate`：
```xaml
<ComboBox ItemsSource="{Binding ThemePresets}" SelectedItem="{Binding SelectedPreset, Mode=TwoWay}">
    <ComboBox.ItemTemplate>
        <DataTemplate><TextBlock Text="{Binding Name}"/></DataTemplate>
    </ComboBox.ItemTemplate>
</ComboBox>
```
WPF 会据 `ItemTemplate` 自动推导只读的 `SelectionBoxItemTemplate`，闭合态随之正确。注意 `DisplayMemberPath` 与 `ItemTemplate` 互斥，不能同时设（运行期会抛异常）。

### 经验
- `DisplayMemberPath` 生成的内部模板**不参与** `SelectionBoxItemTemplate` 推导；`ItemTemplate` 才参与。绑定自定义对象集合且用了自定义 ControlTemplate 时，一律用 `ItemTemplate`，别用 `DisplayMemberPath`。
- `SelectionBoxItemTemplate` 只读，任何"手动补上它"的思路都是死路。

## 修复：自定义主题按钮「新建/编辑/删除」文字被截断

原布局是把「标签 + ComboBox + 三个按钮」塞进同一个 `DockPanel`（横向 Dock）。问题：
- 按钮固定 `Width=56`，对 12pt 中文两字不够（实测最小需要 ~64-68）；
- 内容总宽度 ≈ 70（标签）+ 150（ComboBox）+ 56×3 + 边距 ≈ 400px，而外观区的卡片宽度受窗口宽度限制，常态下卡片根本到不了 400，StackPanel 横向溢出父容器被裁切（截图红框位置）。
- `DockPanel` 没有自动换行能力。

**正解**：拆成两行——`StackPanel` 包两个 `DockPanel`：
1. 第 1 行：「主题预设」+ ComboBox（`MinWidth=160` + `HorizontalAlignment=Right`，让 ComboBox 撑满剩余宽度，避免 150 定宽过窄）。
2. 第 2 行：三个按钮 `StackPanel Orientation=Horizontal HorizontalAlignment=Right`，每个 `MinWidth=68` `Padding=10,0`，让扁平按钮按内容自适应宽度，避免中文被裁。

### 经验
- 中文 12pt 2 字按钮的合理最小宽度：64-68px（`MinWidth` + 内边距），不要写固定 `Width=56`。
- "标签 + 控件 + 控件"的复杂行优先用两行布局：标签/控件行 + 操作行；不要硬塞进一个 `DockPanel`。`DockPanel` 没有 Wrap 能力，溢出即裁切。
- `MinWidth` + `Padding` 比 `Width` 更适合按钮：长内容（如「恢复默认」）会自动撑开，不会被截。

## 修复：主题编辑器预览条会崩溃 / 污染全局主题（潜在 Bug，主动发现）

`ThemeEditorDialog.xaml` 原写法：
```xml
<Border x:Name="PreviewBar" ...>
    <Border.Background><SolidColorBrush Color="{DynamicResource BgDark}"/></Border.Background>
</Border>
```
配合代码 `RefreshPreviewBar()` 里 `if (PreviewBar.Background is SolidColorBrush b) b.Color = _working.BgDark;`（原地改画刷 Color）。

**两个问题**：
1. `MainWindow.SetThemeColor()` 写回资源时调了 `brush.Freeze()`。Frozen 画刷**原地改 Color 会抛 InvalidOperationException**。
2. 即便没 Freeze，那也是全局共享实例，改它等于**边预览边改掉整个 App 的真实主题**（还没点保存就生效了）。

**正解**：预览条不要绑 DynamicResource，改为代码里赋**独立新画刷**：
```csharp
private void RefreshPreviewBar() => PreviewBar.Background = new SolidColorBrush(_working.BgDark);
```
XAML 里去掉 `<Border.Background>` 整段。另外因为原来靠 XAML 提供初值，去掉后**必须在构造函数补调一次 `RefreshPreviewBar()`**，否则预览条初始透明。

### 经验
- **凡是要在运行时改 Brush 的 Color，就绝不能用 DynamicResource 绑全局画刷**：一是 Frozen 抛异常，二是共享实例会串改。要用 `new SolidColorBrush(...)` 整体替换。
- 项目约定：`SetThemeColor()` 会同时替换 `XxxColor` 与 `XxxBrush` 两个资源键，且新画刷一律 `Freeze()`。所以全局主题画刷全都是不可变的。
- 从 XAML 移除初值后，记得在代码里补初始化调用。
